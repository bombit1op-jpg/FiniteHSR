# AGENTS.md — FiniteHSR / Honkai: Star Rail Battle Simulator

## 0. Purpose

Этот файл — **инструкция для coding-agent**, а не полный справочник проекта.

Здесь находятся только правила, которые агент должен соблюдать почти в каждой задаче:
- source-of-truth и порядок чтения документов;
- архитектурные инварианты;
- критические соглашения текущего engine;
- правила работы с raw data;
- правила реализации персонажей / gear / команд;
- verification и debug workflow;
- запреты на опасные shortcuts;
- критерии завершения задачи.

Не дублируй здесь:
- полный список персонажей и их skillset;
- полный список Light Cones;
- историю старых фиксов;
- подробный roadmap;
- длинные debug-транскрипты;
- подробные примеры конкретных китов.

Для этого существуют отдельные документы.

## 1. Source of Truth

Используй источники в следующем порядке.

1. **Текущий запрос пользователя** — что именно требуется сейчас.
2. **Raw game data** — `hsr-data/data/*.json` для значений из датасета.
3. **Mechanics docs** — `docs/combat_mechanics/*.md` для правил конкретной механики.
4. **`TODO.md`** — текущий проверенный статус проекта и порядок работ.
5. **`AGENTS.md`** — инженерные правила и инварианты.
6. **Verification fixtures / tests** — ожидаемое поведение уже проверенных сценариев.
7. **Reference guide** — `reference/hsr_simulator_unified_guide.txt` для целевой архитектуры,
   verification, debug и неочевидных классов механик.
8. **Architecture/reference files** — `reference/hsr_simulator_structure.txt`,
   `reference/hsr_log_format.txt`.
9. **Внешние реализации** (`reference/hsr-optimizer-main`, Fribbels и т.п.) — только
   cross-check, никогда не считать их автоматически каноном.

Если источники конфликтуют:
- не угадывай;
- найди конкретное правило и конкретный код;
- проверь существующие тесты;
- зафиксируй расхождение как known deviation / project decision, если это сознательное решение.

`TODO.md` отвечает на вопрос **«что сейчас делать»**.
`reference/hsr_simulator_unified_guide.txt` отвечает на вопрос **«как должен быть устроен и проверяться engine»**.
`AGENTS.md` отвечает на вопрос **«как агент должен работать с кодом»**.

Главная цель проекта:

> Сделать deterministic, inspectable и verifiable combat engine, а не просто генератор
> правдоподобных чисел.

Текущий приоритет определяется `TODO.md`.

verification или regression.

Особенно не начинай одновременно с engine-задачей:

- новых конусов;
- массовой генерации реликов;

- UI;

## 3. Core Architecture Contract

Целевая модель:

```text
RAW DATA
  ↓
RULE INTERPRETATION
  ↓
BUILD CONFIG
  ↓
TEAM CONFIG
  ↓
ENCOUNTER CONFIG
  ↓
RULES SNAPSHOT
  ↓
BATTLE STATE
  ↓
TIMELINE
  ↓
ACTION
  ↓
ATTACK CONTEXT
  ↓
EVENTS / TRIGGERS
  ↓
EFFECTS / DAMAGE / RESOURCES
  ↓
STATE TRANSITIONS
  ↓
EVENT STREAM
  ├─ Combat Log
  ├─ Debug Trace
  ├─ State Diff
  └─ Damage Trace
  ↓
VERIFICATION / ANALYSIS
  ↓
SWEEP / REGRESSION
```

Не смешивать:

```text
SOURCE DATA
RULE INTERPRETATION
BUILD / TEAM CONFIG
RUNTIME STATE
```

И не смешивать внутри runtime:

```text
character definition
build state
battle state
stage rules
```

### Главный принцип

Существующий simulator должен постепенно двигаться к модели:

```text
Simulator = orchestration
BattleState = mutable state
Timeline = scheduling
Action = what happens
AttackContext = identity/context of an attack
Event = what happened
Trigger = reaction to an event
Effect = state-changing operation
```

Не строй engine вокруг `character.attack()`.

## 4. Non-Standard Mechanics Are First-Class

Никогда не предполагай, что:

```text
Ultimate == Energy Full
Turn == One Ability
Ability == One Attack
Attack == One Hit
Hit == One Damage Event
Damage == HP Loss
FUA == Recursive Attack Call
Summon == Character
Buff == Direct Stat Mutation
Resource == Energy
Alive == Can Act
```

Engine должен быть способен представить как минимум:

```text
- standard Energy;
- alternative Ultimate resources;
- energy threshold Ultimate;
- special-resource Ultimate;
- charges / counters / gauges;
- resource overflow;
- resource that also modifies stats;
- resource generated by another entity's event;
- HP damage vs HP loss vs HP consumption vs redirect;
- persistent battle accumulators;
- state machines / transformations;
- dynamically available ability sets;
- multi-tag attacks;
- reactions / counters;
- scheduled / countdown entities;
- off-turn entities;
- summons / memosprites with explicit ownership;
- joint / multi-source attacks;
- marks and mark transfer;
- zones / fields / auras;
- team-level state;
- pre-battle / Technique state;
- event-driven actions;
- sub-field / alternate combat-space semantics when required by content.
```

**Не решай generic mechanic через `if (kitId === ...)`**, если можно создать reusable primitive.

Character-specific handler допустим, когда механика действительно уникальна и generic abstraction
становится хуже/хрупче.

## 5. Action / Attack / Hit / Trigger Semantics

Всегда различай:

```text
Action
  = одно запланированное или принудительно выполненное действие

Activation
  = одна активация способности/цепочки

Attack
  = логическая атака внутри activation

Hit
  = конкретное попадание

Damage Event
  = конкретное изменение через damage pipeline

Trigger
  = реакция на event
```

Не своди это к одному ID.

Целевая модель `AttackContext`:

```ts
{
  actionId,
  activationId,
  attackId,

  sourceId,
  ownerId,

  type,
  element,

  hitIndex,
  hitCount,

  tags,
  triggerSource
}
```

### `attackNo` vs `attackAct`

В текущем engine:

```text
attackNo / attackSeq
    = identity конкретной атаки

attackAct
    = identity активации
```

`attackNo()` нельзя использовать там, где нужен gate «один раз за activation».
`attackAct()` нельзя использовать там, где нужен gate «один раз за attack».

Это особенно важно для:
- multi-hit;
- FUA;
- retyped hits;
- Additional DMG;
- counters;
- nested actions.

## 6. Turn / Ultimate Contract

### 6.1 Обычный turn

Текущая глобальная конвенция:

```text
charTurn = one action slot
```

Ultimate по умолчанию **заменяет действие этого хода**, а не идёт дополнительно.

`grantExtraTurn` / другие explicit extra-action mechanics — отдельное действие.

Если энергия стала полной во время текущего действия, это не даёт автоматически ещё одно действие
внутри того же turn.

Не использовать старую конвенцию «Ult поверх Basic/Skill».

### 6.2 Ultimate

Ultimate execution не должен быть жёстко связан с обычной Energy.

Концептуально:

```text
UltimateAvailability
    ↓
UltimateActivation
    ↓
UltimateConsumption
    ↓
Action creation / execution
```

Поддерживаемые классы activation:

```text
energy_full
energy_threshold
special_resource_threshold
charges
counter
gauge
state_condition
external_trigger
custom predicate
```

Стандартная Energy — только один вариант.

### 6.3 Current special-ULT cases

Текущий reference/engine contract содержит отдельные non-Energy Ultimate ресурсы,
в частности для Acheron, Castorice, Cyrene, Feixiao, Phainon и Silver Wolf LV.999.

Не создавай fake `energyMax` ради того, чтобы заставить такие Ultimates работать.
Используй подход `resource + availability + consumption`.

Half-threshold Energy — отдельный класс и не должен смешиваться с non-Energy resource.

## 7. Resource Contract

В engine ресурс — это не синоним Energy.

Generic resource должен уметь:

```text
current
max / threshold
optional overflow
owner
lifetime
reset rule
consumption rule
generation sources
stat contribution (если есть)
```

Минимальные resource classes:

```text
Energy
Skill Points
Stacks
Charges
Counters
Gauges
Persistent Accumulators
Team Resources
Special Character Resources
```

Любое изменение ресурса должно идти через API и быть наблюдаемым как state/event transition.

Не делать прямые:

```ts
u.energy += x
sim.sp -= x
```

в местах, где можно использовать resource API.

## 8. HP Semantics

Не смешивать:

```text
incoming damage
HP loss
HP consumption
HP drain
HP redirect
HP restore
revival
```

Если механика реагирует на «HP loss», не заменяй это автоматически на `DamageDealt`.

Если механика требует redirect/interceptor, не прячь её внутрь DamageCalculator без явной семантики.

Целевой паттерн:

```text
Damage calculation
    ↓
Resolved incoming damage
    ↓
HP-change / shield / interceptor layer
    ↓
Actual HP mutation
    ↓
HP-related events
```

Любая прямая мутация HP должна быть классифицирована:

```text
legitimate internal/state mutation
или
engine bypass
```

## 9. State Lifetime

Для любого runtime state сначала определить lifetime:

```text
PER_HIT
PER_ATTACK
PER_ACTIVATION
PER_ACTION
PER_TURN
PER_WAVE
PER_CYCLE
PER_BATTLE
PERSISTENT
```

Перед добавлением нового `rt.foo` зафиксировать:

```text
owner
lifetime
initial value
reset condition
expiration condition
stack rule
source
```

Это обязательно для:
- FUA gates;
- one-per-turn effects;
- buff/debuff duration;
- countdowns;
- accumulators;
- summon state;
- wave/cycle mechanics;
- transformations.

## 10. State Machines / Transformations

Если механика меняет доступные действия или состояние сущности, не моделируй её как простой статический buff.

Используй концепцию:

```text
NORMAL STATE
    ↓
TRANSITION
    ↓
TRANSFORMED STATE
    ↓
STATE-SPECIFIC ABILITIES / RULES
    ↓
EXIT / EXPIRATION
```

State machine должна уметь менять:
- available abilities;
- action permissions;
- timeline presence;
- targeting eligibility;
- stat sources;
- resource rules;
- exit conditions.

`Alive`, `CanAct`, `CanReact`, `CanBeTargeted`, `VisibleOnTimeline` — разные свойства.

## 11. Summon / Memosprite Contract

Не предполагать:

```text
summon == normal character
```

Для summon/memosprite явно определяй:

```text
owner
ownerId
stat source
crit source
timeline behavior
action behavior
lifecycle
spawn event
despawn event
post-action behavior
damage attribution
```

Допустимы разные модели:

```text
normal AV summon
memospite with own AV
event-driven summon
countdown entity
off-turn summon
joint attacker
```

Если summon зеркалит CRIT владельца, предпочитать live lookup текущего значения, если это соответствует

Для debug всегда показывай:

```text
owner
stat source
crit source
timeline source
action identity
owner damage attribution
```

## 12. Timeline Contract

Timeline — единственное место, которое отвечает за scheduling.

Персонажный kit может запросить:

```text
advance
 delay
extra action
immediate action
schedule action
```

но не должен сам реализовывать порядок queue.

Нельзя прятать timeline decisions внутри character logic.

### Advance / Delay / Extra Turn

Это разные семантики:

```text
Action Advance
Action Delay
Extra Turn
Immediate Action
Scheduled Action
```

Не заменять всё одной операцией «100% advance».

### Ordering

Порядок должен быть централизованным и deterministic.

Любой новый fan-out/trigger обязан явно определить:

```text
priority
insertion point
source order
slot order
same-time tie-break
```


## 14. Damage Contract

Damage не должен рассчитываться отдельно в каждом kit.

Целевая цепочка:

```text
Ability / AttackContext
  ↓
Base scaling
  ↓
Source stat
  ↓
Base / flat terms
  ↓
Damage bonuses
  ↓
Crit
  ↓
Weaken
  ↓
DEF
  ↓
RES
  ↓
Vulnerability
  ↓
Mitigation
  ↓
Broken / target-state modifiers
  ↓
Final modifiers
  ↓
Final damage
```

Текущая базовая формула проекта:

```text
DMG = Base × CRIT × (1+Type+Elem+All boost)
    × (1-Weaken)
    × DEFmult
    × RESmult
    × Vulnmult
    × ∏(1-mit)
    × broken/intact modifier
```

Капы и конкретные значения брать из текущих mechanics docs / reference guide,
а не копировать из памяти.

Ключевые проверенные project rules:

```text
CRIT Rate cap = 1.0
RES reduction cap = 90%
RES PEN floor = -100%
Vulnerability bonus cap = 2.50
MaxToughnessMult = 0.5 + maxToughness / 40
```

`MaxToughnessMult /40` — это проектный canon decision; не заменять `/120` из внешнего reference без нового доказательства.

Особые damage paths могут существовать, но должны быть **явными типами/режимами**, а не скрытыми bypass-ами:

```text
DoT
Break
Super Break
True Damage
Elation
Additional DMG
```

## 15. Damage Trace

Каждый сложный damage result должен быть диагностируемым.

Минимум:

```text
source
target
attackType
element
baseDamage
finalDamage
crit roll/rate/result/multiplier
modifier stages
HP before/after
toughness before/after
```

Идеальный stage сохраняет вклад каждого источника:

```text
+24% Sparkle
+20% Light Cone
+18% Relic
+12% Talent
```

Не использовать только pooled multiplier, если источник легко определить.

Финальный damage — недостаточное доказательство корректности.

## 16. Stats Contract

StatResolver — единая точка разрешения статов.

Смысл:

```text
Base
  ↓
Percent modifiers
  ↓
Flat modifiers
  ↓
Conditional / temporary modifiers
  ↓
Final stat
```

**Текущая project convention:** flat HP/ATK/DEF effects представлены как `hpFlat/atkFlat/defFlat`
и применяются после percentage stage; не добавлять их напрямую в base stats без явного решения.

Не писать character-specific stat math внутри kit.

Kit должен создавать effect/modifier.
StatResolver должен знать, как его применить.

Target-conditional stats должны быть явно названы как conditional, а не подменяться глобальным stat.

## 17. Buff / Debuff Contract

Buff/debuff — это state objects, а не прямое изменение числа статов.

Нужны:

```text
id
source
owner/target
stacks
maxStacks
duration
refresh/replace/stack behavior
modifiers
triggers
payload
```

При изменении состояния используйте централизованный lifecycle:

```text
apply
stack / refresh / replace
expire
remove
```

Для duration используйте общий expiration API.
Не копируй вручную `filter(buffs)`-логику в новом месте, если есть общий helper.

`Infinity` / permanent effects должны явно отличаться от тикающих duration.

---

## 18. Break / Toughness Contract

Всегда различай:

```text
HP damage
Toughness damage
Break damage
Super Break
```

Break pipeline должен явно показывать:

```text
hit
→ toughness reduction
→ check break
→ break damage / related effects
→ broken state transition
→ post-break triggers
```

Текущий project rule:

```text
The hit that empties Toughness and its immediate Break DMG
are resolved while target is still considered intact;
Broken flag is set after the Break damage calculation.
```

Новый код не должен менять этот порядок случайным образом.

---

## 19. Ability Availability

Доступные способности могут зависеть от state.

Не предполагай, что у entity навсегда фиксирован:

```text
basic
skill
ult
```

Use the conceptual API:

```text
getAvailableAbilities(entity, state)
```

Состояние может:
- отключить Skill;
- заменить Basic на Enhanced Basic;
- запретить Ultimate;
- дать extra ability;
- разрешить action только вне обычного timeline;
- перевести entity в off-turn режим.

## 20. Targeting Contract

Target selection должен быть отдельным resolver.

Не делать:

```ts
target = enemies[0]
```

в kit-логике.

TargetResolver должен поддерживать, где требуется:

```text
single
blast
AoE
random
lowest HP
highest HP
marked
primary
adjacent
forced
aggro-weighted
fallback target
```

Target selection должен происходить в момент, предусмотренный спецификацией,
а не обязательно в начале всего действия.

Для сложной targeting logic в debug показывать:

```text
rule
candidates
filters
weights
RNG
selected target
fallback reason
```

## 21. Gear Rules

### Light Cones

Raw stats/passive values брать дословно из:

```text
hsr-data/data/lightcones.json
```

Перед изменением проверь raw data.

Superimposition:

```text
SI = 1..5
```

и значение `si` должно проходить через gear hooks.

Не flatten-ить stateful passive, если нормальный event hook может смоделировать её корректно.

### Relics

Разделять:

```text
RelicDefinition
RelicPiece
Build
Runtime effect
```

Проверять независимо:

```text
slot
main stat
substats
roll budget
set activation
conditional passive
stack
refresh
expiration
character interaction
```

`buildGear`/allocator — это **generation/allocation**, а не optimizer.
Не называть его полноценным search/optimization engine.

## 22. Raw Character Data Contract

Для `hsr-data/characters.json` не угадывать поля.

Текущая структура принципиально различает:

### Обычный skill персонажа

```text
characters[N].skills.<id>
  → levels
      → { level, params[] }
```

### Memosprite skill

```text
characters[N].memosprite.skills.<id>
  → level
      → { level, param_list[] }
```

У memosprite skill нет ключа `levels`.

Также:

```text
desc = skill text
notes = optional notes
sp_base = SP metadata where applicable
```

Не используй `description`, если его нет в raw data.

`type_name` и `Maze*` / `MazeAttack` обозначают Technique-related data, а не memosprite.

Перед новым parser/helper сначала смотри реальную структуру JSON.

Не добавляй «терпимые» fallbacks, которые скрывают неверное чтение данных,
если они не нужны документированной совместимости.

## 23. Character Task Workflow

Когда задача касается персонажа:

```text
1. Найти kitId.
2. Найти raw data в characters.json.
3. Проверить правильную форму ladder.
4. Прочитать desc и notes.
5. Прочитать relevant docs/combat_mechanics.
6. Найти текущий KitDef / KitRuntime.
7. Проверить существующие tests / verification fixtures.
8. Определить нужные events, state и hooks.
9. Сделать минимальное изменение.
10. Добавить/обновить regression или verification case.
11. Запустить targeted debug.
12. Запустить общий required gate.
```

Не переносить механику напрямую из текста skill в giant `perform()` без проверки существующих generic primitives.

## 24. Gear / Team Task Workflow

### Gear

```text
1. Read raw data.
2. Verify stat/passive values.
3. Classify effect: static / conditional / stack / duration / trigger / resource.
4. Prefer reusable hook/event.
5. Add a gear delta or passive verification case.
6. Check SI ladder.
7. Check character interaction.
```

### Team

Сначала проверяй:

```text
individual kit
→ pair interaction
→ 3-way interaction
→ full team
```

Не пытайся brute-force все команды.

Используй:

```text
TeamSpec
BuildSpec
EncounterSpec
RulesSnapshot
```

когда соответствующий слой существует/задача требует его.

## 25. Verification Contract

Слова `implemented`, `works`, `verified` — не синонимы.

Для важной механики различай:

```text
Engine support
Character implementation
Scenario verified
Reference verified
Adversarial verified
Known deviation
```

Изменение нельзя считать полностью готовым только потому, что:
- TypeScript компилируется;
- бой запускается;
- финальный damage выглядит правдоподобно.

Готовность означает, где применимо:

```text
relevant unit/scenario test PASS
state assertions PASS
event assertions PASS
numeric trace PASS
invariants PASS
existing regression corpus PASS
```

Не ослабляй matcher, чтобы «протащить» упавший test.

Если требование пока невозможно проверить — пометь его partial / unverified / known deviation,
а не `[x]` без доказательства.

## 26. Test Layers

Используй несколько уровней.

### Unit tests

Изолированные правила:

```text
stats
damage stage
crit
DEF
RES
vulnerability
energy/SP
AV

break

```

### Scenario tests

Минимальный реальный бой:

```text
one character + dummy
support + carry

FUA trigger
summon trigger

```

### Golden tests

Фиксируют:

```text
input/config

expected summary
```

### Regression tests

Каждый найденный bug превращай в воспроизводимый case.

### Property / invariant tests

Проверяют невозможные состояния.

### Determinism

Один и тот же config + seed должен давать одинаковый event/state trace,
а не только одинаковый final damage.

## 27. Invariants

Минимальные engine invariants:

```text
0 <= HP <= maxHP
0 <= Energy <= maxEnergy
0 <= SP <= maxSP
Toughness >= 0
Shield >= 0

no NaN
no Infinity

dead unit cannot perform normal action
expired buff cannot modify stats
invalid action cannot spend resources
invalid Ultimate cannot execute
AV remains valid
entity identity is ID-based
owner attribution is stable
```

Запускай эти проверки после каждого event в test/debug режиме, если это не разрушает производительность массового sweep.

Engine должен падать как можно ближе к событию, которое породило invalid state.

## 28. Debug Protocol

Если поведение отличается от ожиданий:

```text
1. Reproduce with a fixed seed.
2. Reduce to the smallest scenario.
3. Enable DEBUG=5 or DEBUG=6.
4. Compare expected vs actual event stream.
5. Find FIRST DIVERGENCE.
6. Inspect state diff before/after divergence.
7. Inspect DamageTrace if damage is involved.
8. Inspect RNG only if randomness is involved.
9. Classify root cause:
      data
      rule
      ordering
      state lifetime
      resource
      targeting
      damage math
      ownership
10. Add regression coverage.
11. Fix root cause.
12. Re-run full required gate.
```

Не начинай с полного Monte-Carlo sweep, если баг можно воспроизвести на 1–3 действиях.

## 31. RNG Contract

В combat logic нельзя использовать `Math.random()`.

Использовать единую seeded RNG систему.

Для сложной диагностики хранить:

```text
seed
call index
purpose
roll
threshold
result
```

Если после рефакторинга возник RNG divergence, сначала определить,
не изменился ли event ordering / число RNG calls раньше по trace.

## 32. Replay / Hash Contract

Для воспроизводимого запуска достаточно иметь возможность восстановить как минимум:

```text
config
seed
rules/version
```

и получить тот же:

```text
event hash
state hash
```

Checkpoint hashes полезны при больших рефакторингах:

```text
EVENT 100 -> hash A
EVENT 110 -> hash B
EVENT 120 -> hash C
```

Ищи первую точку расхождения, а не сравнивай только финальный результат.

## 33. Known Deviations

Известное расхождение — это не баг, который надо молча «починить».

Перед исправлением:

```text
1. Locate deviation.
2. Identify source/rule.
3. Check if intentional.
4. Add/confirm regression case.
5. Change only if fidelity requires it.
6. Update TODO / deviation registry.
```

Не удаляй `ponytail:` просто ради чистого файла.
Сначала убери причину упрощения и добавь защитный test.

---

## 34. Forbidden Shortcuts

Запрещены без явного обоснования и regression coverage:

1. Прямой stat mutation из character kit.
2. `Math.random()` в боевой логике.
3. Отдельный damage formula внутри конкретного character kit.
4. Bypass общего `sim.hit`/DamagePipeline ради удобства.
5. Display-name как identity владельца/источника.
6. Смешивание activation/attack/hit identity.
7. CharacterId-specific branch в generic engine, если хватает generic primitive.
8. Сведение всех Ultimate к обычной Energy.
9. Сведение всех summon к обычному Character.
10. Сведение любого временного состояния к Buff.
11. Использование final damage как единственного доказательства.
12. Ослабление matcher вместо исправления реализации.
13. Молчащее изменение known deviation без regression test.
14. Giant refactor во время локального механического фикса.
15. Пометка задачи как done без фактического запуска релевантных проверок.

## 35. Handling Direct Mutations

Если найдено:

```ts
hp -= x
hp += x
energy += x
stat += x
```

не переписывай автоматически.

Сначала классифицируй:

```text
A. Legitimate internal mutation
B. Resource operation
C. HP-change semantic
D. Damage/heal pipeline bypass
E. Runtime state assignment
```

Только D обычно требует engine correction.

A/B/C могут быть правильными при наличии соответствующего semantic API.

---

## 36. Data vs Interpretation vs Runtime

Никогда не копируй raw description напрямую в runtime state.

Пример:

```text
RAW DATA
  Skill multiplier = 1.40

RULE INTERPRETATION
  4 hits
  each hit has its own coefficient
  Frozen interaction after selected hit

ENGINE MODEL
  multiHit = 4
  hitDistribution = [...]

RUNTIME
  HIT #1
  HIT #2
  HIT #3
  HIT #4
```

Это позволяет отличить ошибку data parsing от ошибки engine semantics.

## 40. Agent Mindset

При любой задаче сначала спроси:

```text
What is the smallest correct change?
What generic semantic primitive does this require?
What is the exact expected state transition?
What events must be emitted?
What existing behavior must remain unchanged?
How will I prove the change is correct?
```

Цель:

```text
DESCRIPTION
    ↓
SPEC
    ↓
ASSERTIONS
    ↓
EXPECTED EVENTS / STATE
    ↓
ACTUAL EVENTS / STATE
    ↓
FIRST DIVERGENCE
    ↓
REGRESSION
```

Итоговый принцип проекта:

> **Не просто сделать механику работающей. Сделать её наблюдаемой, воспроизводимой и проверяемой.**
